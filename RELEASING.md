# Releasing

Releases are cut from `main`.
`CHANGELOG.md` holds the notes for the current release only.
It is generated by [git-cliff](https://git-cliff.org) from conventional commit messages,
so keep commit subjects in the `type(scope): summary` form.
Notes for earlier releases live in their tagged commits and on the Releases page.

Git tags carry a `v` prefix (for example `v0.2.0`);
the published Docker images are tagged without it (`0.2.0`, `0.2`, `0`).

## Steps

1. Prepare the release.
   Go to **Actions** → **Prepare release** → **Run workflow**,
   enter the new version without the `v` prefix (for example `0.2.0`) and run it.

   The workflow bumps the version in `Cargo.toml` and `Cargo.lock`,
   replaces `CHANGELOG.md` with the git-cliff notes for 0.2.0,
   and opens a `release/0.2.0` pull request labelled `release`.

   The same workflow can be dispatched from a terminal with the GitHub CLI:

   ```sh
   gh workflow run prepare-release.yml -f version=0.2.0
   ```

   or, equivalently, `just prepare-release 0.2.0`.

2. Review and merge the release PR.

3. On the [Releases](../../releases) page, draft a new release.
   Enter the tag `v0.2.0`,
   target `main`,
   click **Generate release notes**
   and publish.

   Publishing pushes the tag.
   The tagged commit already contains the version bump and changelog,
   and the `Release` workflow builds and publishes the multi-arch Docker images to GHCR and Quay.

## Notes

- `CHANGELOG.md` is generated, not edited.
  Grouping and formatting live in `cliff.toml`.
  To preview the next release locally:

  ```sh
  git-cliff --tag v0.2.0 --unreleased
  ```

- The release notes on the GitHub Releases page are still GitHub's own PR-based summary
  and may differ from `CHANGELOG.md`.
- Release PRs are excluded from generated notes via `.github/release.yml`.
- PRs opened with the default `GITHUB_TOKEN` do not trigger the `CI` workflow.
  Add a `RELEASE_TOKEN` repository secret (a personal access token with `repo` scope)
  to get CI on release PRs.
